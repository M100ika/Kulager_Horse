# Правила работы с репозиторием

Для всех участников проекта Kulager: механика, электроника, прошивка,
приложение, документация. Изменения в `main` принимает владелец репозитория
@M100ika.

## Главное

1. В `main` напрямую не пушит никто. Работа идёт в своих ветках и попадает
   в `main` через pull request только после согласования с @M100ika.
2. Всё, что вы делаете, документируется, в том числе в своей ветке: коммиты
   с понятными сообщениями и журнал ветки в [`docs/worklog/`](docs/worklog/).
3. Одна ветка — одна задача. После слияния ветка удаляется.
4. В репозиторий попадает только то, что нужно проекту. Черновики, временные
   файлы, сборки, логи и файлы ИИ-инструментов не коммитятся.
5. Никаких испытаний на лошади без пройденных стендовых испытаний и проверки
   требований из [`docs/safety/`](docs/safety/).

## Среда разработки

| Направление | Чем работать | Что лежит в репозитории |

| Python-инструменты | Python 3.10 или новее, окружение `.venv` в папке инструмента | `requirements.txt` |
| схемы и платы | KiCad 8 или новее (предпочтительно) либо EasyEDA. Одна плата ведётся в одном инструменте от начала до конца | KiCad: проект целиком (`.kicad_pro`, `.kicad_sch`, `.kicad_pcb`, библиотеки проекта). EasyEDA: исходник проекта, выгруженный в файл, а не только ссылка на облако. KiCad 8 импортирует проекты EasyEDA Standard и Pro |
| 3D-моделирование | любой CAD: SolidWorks, Fusion 360, FreeCAD и другие | исходник в формате своего CAD и STEP, см. ниже |
| документация | Markdown, любой редактор | `.md`, картинки рядом в PNG или JPG |

### Формат 3D-моделей

Каждый работает в своём CAD, а открываться модели должны у всех:
в SolidWorks, Fusion 360 и FreeCAD. Родные форматы этих программ друг
с другом не совместимы, поэтому общий формат — STEP.

- Исходник лежит в `mechanical/cad/`: `.SLDPRT`/`.SLDASM`, `.f3d`, `.FCStd`.
  Для каждой детали и сборки в `mechanical/exports/` лежит STEP с тем же
  именем: `cad/parts/rein-drum-rB.FCStd` → `exports/rein-drum-rB.step`.
- STEP обновляется в том же коммите, что и исходник. Иначе коллега в другом
  CAD работает с устаревшей геометрией.
- Экспорт в STEP AP214, единицы — миллиметры. Сборка выгружается целиком,
  одним файлом.
- Покупные изделия (мотор, подшипники, разъёмы) хранятся в
  `mechanical/cad/vendor/` в STEP, как их даёт производитель.
- Чертежи — PDF, контуры для резки — DXF в миллиметрах, модели для
  3D-печати — STL или 3MF. Они обновляются при выпуске ревизии.

## Ветки

- `main` — согласованное состояние проекта. Прямой push, force push и удаление
  `main` запрещены настройками GitHub.
- Новую ветку создавайте от свежего `main`. Имя `<ник>/<тема>` латиницей,
  в kebab-case: `maxat/esp32-two-motors`, `marat/saddle-mount-rb`.
- Несвязанные задачи — в разных ветках, чтобы их можно было проверить
  и принять по отдельности.
- Пушьте свою ветку хотя бы в конце каждого рабочего дня: работа видна
  команде и не пропадёт вместе с ноутбуком.
- Свежие изменения из `main` вливайте в свою ветку: `git merge origin/main`.
  Запушенную историю не переписывайте: `rebase` и `push --force` стирают уже
  задокументированные шаги, на GitHub force push запрещён для всех веток.
- В чужую ветку не пушьте и не удаляйте её без согласия автора.

## Документирование

Документируется всё сделанное, а не только то, что дошло до `main`:

| Что | Где |
|---|---|
| изменения в файлах | сообщения коммитов |
| ход работы: что делали, что проверили, что не получилось, что дальше | журнал ветки `docs/worklog/<ник>-<тема>.md`, формат в [`docs/worklog/README.md`](docs/worklog/README.md) |
| испытания и измерения | протокол в [`docs/testing/`](docs/testing/) |
| инженерные решения | ADR в [`docs/architecture/adr/`](docs/architecture/adr/) |
| как устроена и запускается часть проекта | README этой папки |
| обсуждение задачи | issue на GitHub |

В журнал записываются и действия без файлов: прошили мотор, сменили его
CAN ID, сделали замер, заказали деталь, о чём-то договорились. Запись делается
в тот же день и пушится вместе с работой. Неудачная попытка тоже записывается:
она избавит следующего человека от повторения.

## Коммиты

- Один коммит — одно законченное изменение. Разные задачи в один коммит
  не смешиваются.
- Сообщение на русском. Первая строка — что сделано, до 60 знаков,
  в повелительном наклонении: «Добавить консоль ESP32 для двух моторов»,
  «Исправить знак момента в телеметрии». После пустой строки — зачем
  и что важно знать.
- Добавляйте файлы явно. Перед коммитом проверьте `git status`
  и `git diff --staged`: в коммит попадает только то, что вы собирались
  изменить.

## Как изменения попадают в main

1. Работа в ветке закончена, журнал дописан, README затронутых папок обновлены.
2. Влейте свежий `main` в свою ветку и разрешите конфликты у себя.
3. Пройдите проверки затронутых частей (таблица ниже).
4. Откройте pull request в `main`. Описание подставится из шаблона: что
   сделано, зачем, как проверено, ссылки на журнал и задачу. Если работа не
   закончена, а мнение нужно уже сейчас, откройте pull request как Draft.
5. @M100ika назначается ревьюером автоматически. Замечания исправляйте
   новыми коммитами в ту же ветку, pull request обновится сам.
6. В `main` сливает только @M100ika. После слияния ветка удаляется, при
   необходимости её можно восстановить на странице pull request.

| Часть | Проверка |
|---|---|
| `firmware/`, `tools/ak80-mega-test/` | `pio test -e native` в папке проекта |
| `tools/ak80-gui/` | `.venv/bin/python -m pytest` |
| генераторы CAD в `mechanical/cad/scripts/` | повторить генерацию и `verify-*.py` в FreeCAD, см. [`mechanical/concept-rA.md`](mechanical/concept-rA.md) |
| CAD и схемы | файл открывается без ошибок; STEP обновлён вместе с исходником; чертежи и производственные файлы — только при выпуске ревизии |

## Задачи

- Каждая задача, ошибка или вопрос — отдельный issue. Большую задачу
  разбейте на sub-issues, чтобы части можно было делать параллельно.
- У задачи есть исполнитель (Assignees) и метка области: `mech`, `elec`,
  `fw`, `app`, `tools`, `docs`, `safety`.
- Если задача ждёт другую, отметьте зависимость в issue.
- В описании pull request ссылайтесь на задачу: `Closes #12`. После слияния
  она закроется сама.
- Задачу обсуждайте в issue, а не в личных сообщениях: так решение останется
  в проекте. Нужен конкретный человек — упомяните его через @.

## Файлы

- Имена файлов и папок латиницей, в kebab-case, без пробелов. Исключения —
  служебные файлы GitHub: `README.md`, `CONTRIBUTING.md`, `CODEOWNERS`.
  Документация на русском.
- Исходники лежат отдельно от выходных файлов: `cad/` и `kicad/` против
  `exports/`, `drawings/` и `fabrication/`. Чертежи, файлы для печати
  и производства обновляются при выпуске ревизии, STEP — вместе с исходником.
- Ревизии отмечаются git-тегами: `mech-rA`, `pcb-rA`, `fw-v0.1.0`. Теги
  ставит @M100ika.
- Файлы CAD (`.FCStd`, `.SLDPRT`, `.SLDASM`, `.f3d`) и STEP git не умеет
  сливать. Перед правкой общей сборки или детали напишите в её issue, что
  берёте файл. Один файл одновременно правит один человек.
- Не коммитятся результаты сборки (`.pio/`, `.venv/`, `__pycache__/`), логи
  и записи телеметрии, временные файлы, резервные копии CAD, личные настройки
  IDE. Большая часть уже в [`.gitignore`](.gitignore). Если ваш инструмент
  создаёт новый лишний файл, допишите его в `.gitignore`.
- Никаких секретов и персональных данных: паролей, ключей, токенов, зарплат,
  телефонов. Репозиторий публичный, а запушенный файл остаётся в истории
  и после удаления. Если такое всё же попало на GitHub, сразу сообщите
  @M100ika; ключ или пароль замените.
- GitHub предупреждает о файлах больше 50 МБ и не принимает файлы больше
  100 МБ, через браузер — больше 25 МБ. Репозиторий лучше держать в пределах
  1 ГБ. Большие выходные файлы выкладываются в Releases.

## ИИ

ИИ-помощниками пользоваться можно: для кода, текстов, расчётов, поиска.
Главное — не мусорить в проекте. В репозитории результат работы с ИИ не должен
отличаться от аккуратной ручной работы: ни лишних файлов, ни следов
инструмента, ни непроверенного текста.

- За всё, что вы коммитите, отвечаете вы. Каждую строку кода и каждое
  утверждение в тексте вы должны понимать. Не понимаете — не коммитьте.
- Файлы ИИ-инструментов в репозиторий не попадают: `CLAUDE.md`, `AGENTS.md`,
  `GEMINI.md`, `.claude/`, `.codex/`, `.cursor/` и подобные. Известные уже
  в `.gitignore`. Если ваш инструмент создаёт новые, допишите их в раздел
  «Локальные настройки и инструкции инструментов разработки».
- Побочные продукты не коммитятся: планы, «итоги», заметки, выгрузки диалогов,
  временные скрипты, копии файлов с `-v2`, `-new`, `-final`, `-old`.
- Новых документов не плодите: дополняйте существующий README или документ.
  Текст короткий, по делу, в стиле проекта.
- ИИ меняет только то, что относится к задаче. Переформатирование,
  переименования и «улучшения» посторонних файлов откатывайте. Перед каждым
  коммитом смотрите `git diff`.
- Числа и факты сверяйте с первоисточником и давайте ссылку: пределы, моменты,
  размеры, распиновки, характеристики из даташитов. ИИ уверенно выдаёт
  правдоподобные, но неверные значения, а здесь от них зависит безопасность
  лошади и людей.
- Код, написанный с ИИ, проходит те же проверки и ревью, что и любой другой.
- Никаких подписей инструмента в коммитах, pull request и файлах:
  `Co-Authored-By` с ИИ, «Generated with …» и подобного.
- Не отправляйте в ИИ-сервисы пароли и ключи, персональные данные
  и материалы, которые команда не собирается публиковать.

## Шпаргалка

```bash
# начать задачу
git switch main
git pull
git switch -c maxat/esp32-two-motors

# сохранить работу
git status
git diff
git add firmware/src/main.cpp docs/worklog/maxat-esp32-two-motors.md
git commit                                  # откроется редактор для сообщения
git push -u origin maxat/esp32-two-motors   # в первый раз, дальше git push

# влить свежий main в свою ветку
git fetch origin
git merge origin/main
```

После первого push GitHub предложит открыть pull request: кнопка
«Compare & pull request» на странице репозитория.
